1. Jevとは何か

Jevは、文章を生成するチャットモデルではなく、ソフトウェアの中で使う判断専用モデルです。

TypeSafe AIはJevを最初の「System One Model」と説明しています。入力として、判断対象の文章やJSONである state と、回答形式を決めた questions を渡します。Jevは説明文を生成せず、あらかじめ定めた候補、段階、または「はい」の確率を構造化データとして返します。[1][2]

文章を生成しない返すのは、「はい」の確率、候補名、候補別確率などです。
候補を先に決めるChoiceでは、回答可能な選択肢を呼び出し側が定義します。
確率も返す単なるラベルではなく、判断の不確実性を数値として扱います。
公開範囲: API仕様とPython／JavaScript SDKは公開されていますが、Jev本体の重み、詳細アーキテクチャ、完全な学習方法は公開されていません。Jevそのものはオープンウェイトモデルではありません。

三つの質問形式

形式リクエストで送る質問リターンで受け取る値
Noultype: noul と、一つの「はい／いいえ」命題を instructions に入れる「はい」の確率 noul
Choicetype: choice、質問を instructions、固定候補を criteria に入れるchoice、候補別 probabilities、confidence
Scoretype: score、質問と順序付き段階を送る段階の期待値、段階別確率、confidence

本稿は、ご要望の中心であるNoulとChoiceに絞って説明します。

2. Jevへのリクエストとリターンの全体像

Jevへは、評価対象の state、利用モデルの model、型付き質問の questions を送ります。一つのリクエストにNoulとChoiceを混在させられます。リターンでは、各質問がリクエスト時と同じ質問IDの下に入ります。[1][3][4]

送るリクエスト（POST /v1/systemone）
{
  "model": "jev-latest",
  "state": "商品を返品したので、代金を返してください。",
  "questions": {
    "返金を希望しているか": {
      "type": "noul",
      "instructions": "顧客は返金を希望していますか。"
    },
    "担当部署": {
      "type": "choice",
      "instructions": "どの担当部署が対応すべきですか。",
      "criteria": {
        "請求担当": "返金、請求、支払いの問題",
        "技術担当": "製品やサービスの技術的不具合",
        "その他": "上記に当てはまらない問題"
      }
    }
  }
}
→
返るリターン
{
  "model": "jev-1.13.0",
  "answers": {
    "返金を希望しているか": {
      "type": "noul",
      "noul": 0.99
    },
    "担当部署": {
      "type": "choice",
      "choice": "請求担当",
      "confidence": 0.97,
      "probabilities": {
        "請求担当": 0.98,
        "技術担当": 0.01,
        "その他": 0.01
      }
    }
  }
}

構造を説明するための日本語合成例です。APIのフィールド名は公式仕様に合わせて英語のまま記載しています。

リクエスト側のフィールド

フィールド何を入れるか

stateJevに判断させる対象。文章、オブジェクト、配列を渡せる

type質問形式。Noulなら noul、Choiceなら choice

criteriaNoulでは任意の真偽基準、Choiceでは候補名と説明

フィールド日本語での意味登場する形式
answers質問IDごとの回答。IDはリクエストの questions と対応する両方

3. Noulには何を送り、何が返るか

Noulは、一つの「はい／いいえ」質問または真偽命題に対して、「はい」または「真」の確率を一つ返す形式です。

送るNoulリクエスト
{
  "model": "jev-latest",
  "state": "商品を返品したので、代金を返してください。",
  "questions": {
    "返金希望": {
      "type": "noul",
      "instructions": "顧客は返金を希望していますか。"
    }
  }
}
→
返るNoulリターン
{
  "model": "jev-1.13.0",
  "answers": {
    "返金希望": {
      "type": "noul",
      "noul": 0.99
    }
  }
}

リクエストで付けた質問ID 返金希望 が、そのままリターンの answers 内のキーになります。Noulでは criteria は任意で、必要なら「何をはい／いいえと数えるか」を追加できます。

Noulの最重要点

noul: 0.90 は「はいである確率が90%」。noul: 0.10 は「はいが10%、いいえが90%」です。0.10を「自信が10%」とは読みません。

戻り値読み方
noul: 0.99非常に強い「はい」。「いいえ」は約0.01
noul: 0.75「はい」寄りだが、不確実性が残る
noul: 0.50「はい」と「いいえ」が同程度
noul: 0.20「いいえ」寄り。「いいえ」は約0.80
noul: 0.01非常に強い「いいえ」。「いいえ」は約0.99

Noulには別の confidence フィールドがありません。二値分布は、「はい」の確率一つが分かれば、「いいえ」の確率を 1 − noul で求められるためです。[3]

4. Choiceには何を送り、何が返るか

Choiceは、呼び出し側が用意した候補の中から一つを選び、同時に全候補の確率分布を返します。

choice候補別確率が最も大きい候補名。
probabilities全候補の確率。全体で約1になる。
confidence分布が一候補へ集中している程度の要約。

明確なChoiceのリクエストとリターン

送るChoiceリクエスト
{
  "model": "jev-latest",
  "state": "同じ金額が二度引き落とされました。",
  "questions": {
    "担当部署": {
      "type": "choice",
      "instructions": "どの担当部署が対応すべきですか。",
      "criteria": {
        "請求担当": "請求や支払いの問題",
        "技術担当": "技術的不具合",
        "その他": "上記以外"
      }
    }
  }
}
→
返るChoiceリターン
{
  "model": "jev-1.13.0",
  "answers": {
    "担当部署": {
      "type": "choice",
      "choice": "請求担当",
      "confidence": 0.97,
      "probabilities": {
        "請求担当": 0.98,
        "技術担当": 0.01,
        "その他": 0.01
      }
    }
  }
}

choice だけでなく、請求担当が0.98、他候補が0.01ずつであることを一緒に読みます。候補間に明確な差があるため、confidenceも高くなります。

同じリクエスト形式でも、入力が曖昧ならリターンも分かれる

送るChoiceリクエスト
{
  "model": "jev-latest",
  "state": "商品が届かず、もう不要なので返金したい。",
  "questions": {
    "担当部署": {
      "type": "choice",
      "instructions": "最初に対応すべき部署はどこですか。",
      "criteria": {
        "配送担当": "未着や配送遅延",
        "返品担当": "返品や交換",
        "請求担当": "返金や支払い"
      }
    }
  }
}
→
返るChoiceリターン
{
  "model": "jev-1.13.0",
  "answers": {
    "担当部署": {
      "type": "choice",
      "choice": "配送担当",
      "confidence": 0.18,
      "probabilities": {
        "配送担当": 0.45,
        "返品担当": 0.45,
        "請求担当": 0.10
      }
    }
  }
}

形式上は一つの choice が返りますが、分布を見ると配送担当と返品担当が同程度です。choice だけを読んで「配送担当で明確に決まった」と扱ってはいけません。

confidenceは候補の生の確率ではありません。 公式資料では、Choiceの確率分布の形から計算する0〜1の要約統計と説明されています。正確な計算式は公開仕様になっていません。したがって、実務では confidence だけでなく全 probabilities を保存するのが安全です。[4][5]

5. Noulの日本語QA例

すべて「送るリクエスト」と「返るリターン」を一組で示します。各例のリクエストには共通して model: "jev-latest" を指定するものとします。数値は日本語入力に対するJevの実測値ではなく、入出力の読み方を示す説明用例です。

Noul例1 — 明確な「はい」
送るリクエストstate: 商品を返品したので、代金を返してください。
questions.返金希望.type: noul
questions.返金希望.instructions: 顧客は返金を希望していますか。
返るリターンanswers.返金希望.type: noul
answers.返金希望.noul: 0.99
日本語で読むと: 「はい」の確率99%

リクエストの質問ID「返金希望」に対応して、同じIDの下にNoul値が返ります。

Noul例2 — 返金不要が明示された「いいえ」
送るリクエストstate: 商品はそのまま使います。返品も返金も必要ありません。領収書だけ再発行してください。
questions.返金希望.type: noul
questions.返金希望.instructions: 顧客は返金を希望していますか。
理想的なリターンanswers.返金希望.type: noul
answers.返金希望.noul: 0.01
日本語で読むと: 「はい」1%、「いいえ」99%

返金とは無関係な話題を置くのではなく、「返金は必要ない」と明記しています。したがってNo.3の情報不足例とは異なり、明確な「いいえ」です。

Noul例3 — 判断材料が不足
送るリクエストstate: 注文について確認したいことがあります。
questions.返金希望.type: noul
questions.返金希望.instructions: 顧客は返金を希望していますか。
返るリターンanswers.返金希望.type: noul
answers.返金希望.noul: 0.50前後
日本語で読むと: 「はい」と「いいえ」が同程度

stateに返金の情報がないため、命題をどちらとも決めにくい場合の説明用リターンです。

Noul例4 — 確定した命題
送るリクエストstate: 通常の整数算術を前提とする。
questions.命題判定.type: noul
questions.命題判定.instructions: 1足す1は2ですか。
理想的なリターンanswers.命題判定.type: noul
answers.命題判定.noul: 1.00
日本語で読むと: 「はい」の確率100%

命題自体の理想値は1です。ただし公式資料は、Jev 1.13を計算機として使わず、算術はコードで処理するよう勧めています。

Noul例5 — 公平なコイン
送るリクエストstate: 偏りのないコインを、これから1回投げる。
questions.表が出るか.type: noul
questions.表が出るか.instructions: 次は表が出ますか。
理想的なリターンanswers.表が出るか.type: noul
answers.表が出るか.noul: 0.50
日本語で読むと: 表50%、裏50%

質問は「表が出るか」という一つの命題なので、Noulは「はい」に当たる表の確率を返します。

Noul例6 — 公平な6面サイコロ
送るリクエストstate: 偏りのない6面サイコロを、これから1回振る。
questions.一が出るか.type: noul
questions.一が出るか.instructions: 次に出る目は1ですか。
理想的なリターンanswers.一が出るか.type: noul
answers.一が出るか.noul: 1/6 ≈ 0.167
日本語で読むと: 1が出る16.7%、1以外83.3%

Noulでは「1が出る」という命題を評価するため、1/6が「はい」の確率になります。

Noul例7 — 個人情報の検出
送るリクエストstate: 連絡先欄に、氏名［例示用氏名］と電話番号［例示用番号］が記載されています。
questions.個人情報.type: noul
questions.個人情報.instructions: この文章に個人情報が含まれていますか。
理想的なリターンanswers.個人情報.type: noul
answers.個人情報.noul: 0.99
日本語で読むと: 「はい」の確率99%

実在情報を使わないプレースホルダーですが、項目として氏名と電話番号が含まれるため、個人情報を含むという命題は明確に「はい」です。

Noul例8 — 承認条件の充足判定
送るリクエストstate: 経費申請額は8万円。5万円超は部長承認が必要だが、部長承認はまだない。
questions.承認条件.type: noul
questions.承認条件.instructions: この申請は支払い実行の承認条件を満たしていますか。
理想的なリターンanswers.承認条件.type: noul
answers.承認条件.noul: 0.01
日本語で読むと: 「いいえ」の確率99%

規程条件と申請状態を照合する例です。必要な部長承認がないので「いいえ」が理想です。

6. Choiceの日本語QA例

Choiceでは、リクエストの criteria に候補名と各候補の説明を入れます。以下もすべて、送る内容と返る内容を一組にした説明用例です。

Choice例1 — 明確な担当部署
送るリクエストstate: クレジットカードから同じ金額が二度引き落とされました。
questions.担当部署.type: choice
instructions: どの担当部署が対応すべきですか。
criteria: 請求担当／技術担当／その他（各候補の説明も送る）
返るリターンanswers.担当部署.choice: 請求担当
probabilities: {請求担当: 0.98, 技術担当: 0.01, その他: 0.01}
confidence: 0.97

リクエストで定義した候補のうち請求担当が選ばれ、候補別確率とconfidenceも同時に返ります。

Choice例2 — 二つの候補で迷う
送るリクエストstate: 商品がまだ届きません。もう不要なので返金してください。
questions.担当部署.type: choice
instructions: 最初に対応すべき担当部署はどこですか。
criteria: 配送担当／返品担当／請求担当
返るリターンanswers.担当部署.choice: 配送担当（同率時の代表値の例）
probabilities: {配送担当: 0.45, 返品担当: 0.45, 請求担当: 0.10}
confidence: 0.18

リターンの choice は一つでも、全分布を見ると配送担当と返品担当が同程度です。

Choice例3 — 「その他」が必要
送るリクエストstate: サービスを退会して、登録情報を削除したいです。
questions.問い合わせ種類.type: choice
instructions: 問い合わせの種類はどれですか。
criteria: 請求／技術的不具合／その他
返るリターンanswers.問い合わせ種類.choice: その他
probabilities: {請求: 0.02, 技術的不具合: 0.01, その他: 0.97}
confidence: 0.96

リクエストの候補が現実を網羅しない場合に備え、「その他」や「該当なし」も候補として送ります。

Choice例4 — 公平なコイン
送るリクエストstate: 偏りのないコインを、これから1回投げる。
questions.出る面.type: choice
instructions: 次に出る面はどちらですか。
criteria: 表／裏
理想的なリターンanswers.出る面.choice: 表（同率時の代表値の例）
probabilities: {表: 0.50, 裏: 0.50}
confidence: 0

リクエストは二候補から一つを選ばせますが、理想的な分布は同率です。choice より全候補の確率を重視して読みます。

Choice例5 — 公平な6面サイコロ
送るリクエストstate: 偏りのない6面サイコロを、これから1回振る。
questions.出る目.type: choice
instructions: 次に出る目はどれですか。
criteria: 1／2／3／4／5／6
理想的なリターンanswers.出る目.choice: 1（同率時の代表値の例）
probabilities: {1: 1/6, 2: 1/6, 3: 1/6, 4: 1/6, 5: 1/6, 6: 1/6}
confidence: 0

リクエストで指定した六候補は同率です。回答欄の数字一つより、全候補が1/6というリターンの分布が重要です。

Choice例6 — 明確な感情判定
送るリクエストstate: すぐに対応していただき、本当に助かりました。ありがとうございます。
questions.感情.type: choice
instructions: この文章の感情はどれですか。
criteria: 肯定的／中立／否定的／判断不能
返るリターンanswers.感情.choice: 肯定的
probabilities: {肯定的: 0.98, 中立: 0.01, 否定的: 0.005, 判断不能: 0.005}
confidence: 0.97

リクエストのstateに感謝が明示されているため、リターンでは一候補へ確率が集中します。

Choice例7 — 文章の言語判定
送るリクエストstate: この商品は明日発送予定です。
questions.言語.type: choice
instructions: この文章で主に使われている言語はどれですか。
criteria: 日本語／英語／日本語と英語の混在／その他
理想的なリターンanswers.言語.choice: 日本語
probabilities: {日本語: 0.995, 英語: 0.001, 日本語と英語の混在: 0.002, その他: 0.002}
confidence: 0.99前後

文章全体が日本語なので、一候補が明確に優勢になる例です。

Choice例8 — 文書種類の判定
送るリクエストstate: 請求番号A-104、支払期限10月31日、合計金額55,000円（税込）
questions.文書種類.type: choice
instructions: この文書の種類はどれですか。
criteria: 請求書／契約書／履歴書／その他
理想的なリターンanswers.文書種類.choice: 請求書
probabilities: {請求書: 0.98, 契約書: 0.005, 履歴書: 0.005, その他: 0.01}
confidence: 0.97前後

請求番号、支払期限、合計金額という特徴から、請求書が明確に優勢です。

Choice例9 — 中立的な連絡文
送るリクエストstate: 資料を受け取りました。内容を確認して、明日までに連絡します。
questions.感情.type: choice
instructions: この文章の感情はどれですか。
criteria: 肯定的／中立／否定的／判断不能
理想的なリターンanswers.感情.choice: 中立
probabilities: {肯定的: 0.02, 中立: 0.92, 否定的: 0.02, 判断不能: 0.04}
confidence: 0.89前後

感謝や不満ではなく、受領と今後の予定を事務的に述べているため、中立が理想です。

7. 同じサイコロをNoulとChoiceで聞くと何が違うか

質問形式リクエストで送る内容理想的なリターン
Noultype: noul
instructions: 次の目は1ですか。		noul: 1/6。1という命題の「はい」の確率
Choicetype: choice
instructions: 次の目はどれですか。
criteria: 1／2／3／4／5／6		各候補が1/6。どれか一つが choice に入り、候補間の優劣がないため confidence: 0
結論

Noulの 1/6 とChoiceの confidence: 0 は、同じ数値を表しているのではありません。前者は「1が出る確率」、後者は「6候補の中に突出した候補がないこと」を表します。

Choiceと複数Noulも同じではない

Choiceは候補同士を比較し、候補別確率の合計が約1になります。一方、「請求問題か」「配送問題か」を別々のNoulで聞くと、それぞれを独立した「はい／いいえ」の命題として評価します。一つの問い合わせが請求問題でも配送問題でもあるなら、両方のNoulが高くなることがあります。公式資料も、Choiceは相対的な選択、Noulは絶対的な命題評価であり、別質問間の数値関係を自動的に仮定しないよう注意しています。[6]

8. Jevに類似する公開モデル

Jev本体は非公開ですが、同じようにstateと型付き質問から候補別確率を返す公開実装があります。API形状が同じでも、モデルの判断特性や確率の調整状態まで同じとは限りません。

名称方式特徴
LayaModernBERT／mmBERT系の判断モデル小型、多言語版、Jev互換サーバー
KevQwen系モデルと判断用head複数サイズと公開モデルカード
Open-JevQwen系LoRAと判断用head2B／9B／27B、学習・評価資料を公開
AnyJev既存LLMのlogitや中間表現を利用既存の公開LLMを型付き判断へ変換
open-jevKev等をTransformers.jsで実行ブラウザのWebGPU／WASMでローカル実行
